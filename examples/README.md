# 本地审批与幂等恢复样例

这是为求职作品集在 **2026-11-10 新写**的教学样例，使用 Python 标准库和合成文稿。不包含线上系统源码、真实账号、简历、公司资料或历史业务指标；代码演示的行为不能作为既有线上成绩。

## 运行

需要 Python 3.9 或更新版本，不安装任何第三方依赖。PowerShell 进入本目录后执行：

```powershell
python .\editorial_workflow.py --self-check
```

脚本会在本目录 `.tmp` 下创建本次独有的临时 SQLite 数据库，启动一个新的 Python 子进程验证恢复，最后清理本次临时数据库。它不读取真实业务数据，不发起网络请求，也不会调用微信、邮件或任何发布服务。

## 演示的行为

文稿状态依次为 `draft → reviewed → approved → simulated_sent`。审批摘要绑定文档 ID、正文和 `prompt_version`；正文或提示版本修改会退回 `draft` 并清空审批。发送意图一旦持久化，就保留原文和原幂等键；要修改必须另建文稿，避免覆盖待恢复操作。

模拟发送分为三个独立事务：先写调用方 `pending` 操作，再由本地模拟接收端写入唯一回执，最后确认调用方状态。自测在接收端回执提交后故意抛出超时；调用方仍显示 `pending`，文稿仍是 `approved`。重启 Python 进程后，先按同一幂等键查询接收端回执，查到后更新调用方状态，不再次提交接收端。

`operations` 对幂等键和文档各有唯一约束；相同键与不同 payload 冲突时失败，同一文档换键重复发送也失败。`receiver_calls` 记录模拟接收端提交次数，自测要求超时恢复后仍为 1；`receipts` 记录持久化回执，自测要求只有 1 条。这同时检查“没有再次提交”和“没有重复业务结果”。

## 自测覆盖

- 未经审批不能发送。
- 改正文后旧审批失效。
- 改提示版本后旧审批失效。
- 回执落库后丢响应，新进程先查回执恢复，不重复提交。
- 相同幂等键、不同 payload 被拒绝。
- 已发送文稿的历史及原操作键不能被改写。

完整通过时，最后一行是：

```text
SELF-CHECK PASSED: 6 checks; no network or external publishing
```

## 边界与面试可讲的取舍

这是**同一 SQLite 文件中的调用方和接收端模拟**，通过分离事务制造“业务已落库、响应未收到”的窗口。它不是分布式 exactly-once 实现，也没有真实消息传输、并发压测或远端服务故障测试。远端查询超时、回执过期、服务端幂等契约、恢复重试预算等，还需要真实接口与故障注入验证。

`approve()` 仅要求调用方显式提供一个模拟审批人标识，未接入身份认证；测试里的审批调用用于构造合成场景，不证明真实人工已经审核。产品中应由可信身份与权限服务校验审批人，审批绑定具体内容、提示版本和允许动作，模型自身不能授予执行权限。

本例优先让状态、持久化和失败窗口可以读懂。进一步的审批撤销、并发发送与编辑竞争、重试调度和操作审计，应在需求明确后再实现，不据此样例宣称可直接用于生产。
